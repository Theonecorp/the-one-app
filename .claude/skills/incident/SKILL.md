# /incident — 현장 오류 대응

직원 폰에서 난 문제다. **고치기보다 먼저 "이미 고쳐졌는가 · 직원 자료는 안전한가"** 를 확인한다.
(2026-11-13: 다른 세션이 이미 고쳐 머지한 것을 모르고 같은 수정을 또 만들었음 → 0단계)

## 0. 이미 고쳐졌나 (1분)
1. `git fetch -q origin main && git log --oneline -15 origin/main` — 같은 증상을 고친 커밋이 있나 (오류 문구 · 화면 이름으로 `git log origin/main --grep=…`).
2. 열린 PR 도 본다 (GitHub MCP `list_pull_requests`).
3. `node tools/live-status.mjs` — 배포된 앱 버전 · 서버 규칙 · 서버 함수가 main 과 같은가.
   - main 에 고침이 있고 배포도 됐다 → **직원 폰이 옛 앱**일 뿐이다. 4단계(직원 안내)로.
   - main 에 있는데 배포 전 → 배포가 할 일 (관리자 세션: `node tools/fbhost.mjs . apply` · 규칙이면 `node tools/deploy-rules.js` — 규칙 반영은 관리자에게 먼저 묻는다).

## 1. 직원 자료부터 지킨다
- 폰 보관함(📤 아직 회사로 안 간 주문 · `theone.outbox.v1`)에 있는 것은 **폰에만** 있다. 직원에게 "폰에서 지우기"를 누르지 말라고 먼저 전한다.
- 라이브 Firestore 는 **읽기만**. 고쳐 쓰기(문서 수정 · 칸 지우기)는 관리자에게 먼저 묻는다 (CLAUDE.md). 서비스 계정(`FIREBASE_*`)이 없는 세션은 읽지도 않는다.

## 2. 증거로 원인 좁히기
1. 스크린샷의 오류 문구 → `grep -rn` 으로 화면 · 함수 찾기 (`src/*-txt.js` · `i18n.json` 문구도).
2. 해당 문서를 읽기만 해서 서버 모양을 본다 (REST `runQuery` · 문서 id 로). 폰 사본과 다른 칸이 있나 — **서버에만 있는 칸**(다른 화면 · 사무실이 붙인 칸)이 있으면 통째 덮어쓰기(set)가 그 칸을 지우려다 규칙에 막히는 모양이다.
3. 권한 문제면 `tools/rules-test.mjs` 를 복사해 **그 문서 모양 그대로** 케이스를 만들어 돌린다 (`firebaserules projects:test` · 자료를 읽거나 쓰지 않음). 지금 방식 DENY · 고친 방식 ALLOW 가 둘 다 나와야 원인 확정.
4. 언제부터인가: `node tools/impact.mjs <의심 커밋>~1..<의심 커밋>` — 그 변경이 끊은 연결을 본다.

## 3. 고치기
`/ship` 을 따른다. 오류를 재현하는 시험(고치기 전 FAIL · 고친 뒤 PASS 를 직접 확인)을 새 번호로. 규칙을 고쳤으면 `tools/rules-test.mjs` 에 케이스 추가.

## 4. 직원 안내 · 확인
- 고침이 배포되면 직원에게: 앱을 **완전히 닫았다 다시 열기** (옛 앱이 남아 있으면 한 번 더) → 다시 보내기.
- 그 문서를 다시 읽어 실제로 고쳐졌는지 확인하고 보고한다: 원인(한두 줄) · 고친 버전 · 직원이 할 일 · 남은 일.
