# /ship — 변경 한 번의 순서 (CLAUDE.md 「변경 한 번의 순서」 를 빠짐없이)

**목표: 있던 연결을 잃지 않는다.** 직원 폰은 앱을 다시 열 때까지 옛 버전이고, 폰에는 옛 버전이 저장한 자료가 남아 있으며,
다른 화면 · 사무실이 같은 문서에 칸을 붙인다. 새 코드 · 새 규칙은 이 셋을 모두 받아야 한다.

## 1. 시작
1. 요청한 사람의 역할과 영역 확인 (CLAUDE.md 표). 영역 밖이면 최소한으로 · PR 설명 맨 위 `영역 밖 변경: …`.
2. `sh tools/sync-main.sh` — 다른 세션의 변경부터 합친다.
3. 바꿀 기능의 시험을 `test/INDEX.md` 에서 찾아 **먼저 읽는다** (시험이 명세).

## 2. 고치기 전에 연결 확인
`src/` 를 고친 뒤(커밋 전에도 됨) `node tools/impact.mjs` 를 돌리고 **⚠️ 먼저 볼 것** 을 하나씩 처리한다:
- **통째 덮어쓰기(set)** 경고: 그 문서에 다른 곳이 붙이는 칸이 있거나 규칙이 칸 단위면, 서버 문서를 읽어 없는 칸을 이어 붙이거나 `update`/`merge` 로. 가져오기 · 일괄 저장은 언제나 `merge`/`update` (`users` 는 절대 덮어쓰지 않음).
- **📱 폰 저장 자료**: 옛 버전이 저장한 모양(필드가 없거나 옛 이름)도 새 코드가 읽고 보내는지 — 시험에 옛 모양 자료를 넣는다.
- **🔐 규칙 바뀜**: 새 규칙이 **옛 앱의 쓰기도** 받는지 `tools/rules-test.mjs` 에 옛 모양 · 새 모양 케이스 둘 다. 화면보다 규칙을 먼저 넓히고, 좁히는 것은 옛 앱이 다 바뀐 뒤에.
- **바뀐 함수를 부르는 곳**: 부르는 화면마다 기대가 그대로인지.
- **같이 돌릴 시험**: 목록의 시험을 돌린다.

## 3. 고치기 · 시험
1. `src/` 수정 → `sh build.sh` (npx esbuild 금지).
2. 새 기능 · 고친 버그 = 새 시험 `test/tNNN.js` (다음 번호 · 첫 줄 `/* vX.Y.Z 시험 — 무엇을 지키는지 */`). 버그면 **고치기 전 FAIL 을 직접 확인**한 뒤 고친다. `node test/index.js` 로 INDEX 갱신.
3. 새 UI 문구 → `node tools/i18n.js add '한글' 'English' 'Português'` (UI 에 사람 이름 금지).
4. 화면을 바꿨으면 그 화면을 쓰는 옛 시험도 고친다.

## 4. 푸시 전
1. 커밋 (한국어 · 모델 이름 없음 · 비밀값 없음).
2. `sh tools/sync-main.sh` — 버전 세 곳을 main 다음 번호로 · app.js 재빌드 · i18n 합치기. 충돌이 남으면 진짜 src 충돌만 손으로.
3. **`sh test/run-par.sh` 전부 통과** (하나라도 ❌ 면 푸시하지 않는다 — CI 실패 메일이 관리자에게 감).
4. 푸시 → PR (설명: 무엇 · 왜 · 시험 · `배포 필요: …` · 영역 밖 변경).

## 5. 머지 · 배포 (세션 권한에 따라)
- 관리자 세션: `/merge-deploy` 를 따른다 (check 초록 → squash → main 맞춤 → 배포 → `node tools/live-status.mjs`).
- 디자인 담당: PR 까지. 창고 매니저: 큰 틀(CODEOWNERS) 밖이면 머지 · Hosting 배포까지.
- PR 이 머지되기 전에 main 이 움직이면 `sh tools/sync-main.sh` 를 다시.
